# ロードマップ

未実装の作業と、その判断材料をまとめたもの。GitHub の issue で管理していた内容をここへ移した。

設計の背景は [`adr/`](adr/) を、詳細な仕様は [開発ドキュメント](pii-guard-development-doc.md) を参照。

## 現在地

個人のPOCとして、**ChatGPT で送信を止めて確認ポップアップを出し、マスクして送り直す**ところまで動作する。

| 実装済み | 内容 |
| --- | --- |
| 検出エンジン | 正規化・チェックディジット・文脈キーワードのスコアリング・判定理由 |
| 検出ルール | 保険者番号、マイナンバーの2種 |
| 確認ポップアップ | closed Shadow DOM、`isTrusted` 検証、フォーカストラップ |
| イベント捕捉 | Enter・送信ボタン・フォーム送信・貼り付け・ドロップ |
| サイトアダプタ | ChatGPT（＋汎用セレクタのフォールバック） |
| ビルド時チェック | 外部通信APIと `console` 出力の混入を検出し、CIで落とす |

実機確認の結果は [動作確認の記録](#動作確認の記録) を参照。

## 次にやること

### 1. 検出ルールを増やす

現在は保険者番号とマイナンバーの2種のみ。チェックディジットを持つ種別と持たない種別の両方の経路を通せるため、縦一本の確認にはこれで足りるという判断で絞ってある。

追加する種別と、調査で確定した設定は次のとおり（根拠は [調査記録](research/2026-09-21-kouhi-koukikoureisha-number-format.md)）。

| 種別 | 桁構成 | 設定 |
| --- | --- | --- |
| 公費負担者番号 | 8桁 | `validator: 'luhn'` |
| 公費負担医療の受給者番号 | 7桁 | `validator: 'luhn'`、`requireKeyword: true` |
| 後期高齢者医療 被保険者番号 | 8桁 | `validator: null`、`requireKeyword: true`（全国共通の検証方式が存在しない） |
| 被保険者記号・番号 | 可変長 | `kind: 'regex'`、キーワード必須 |
| 基礎年金番号 | 10桁 | `validator: null`、`requireKeyword: true` |
| クレジットカード番号 | 14〜16桁 | `validator: 'luhn'` |
| 電話番号・メールアドレス | ― | `kind: 'regex'` |

残りの種別は開発ドキュメント 3.1 の一覧を参照。

### 2. 評価コーパスを作って閾値を決める

スコアの配点と閾値、キーワード辞書はチューニングが前提の値になっている。

- 業務文書を模した文章（議事録、問い合わせ対応メモ、請求書説明、コード断片など）を用意する
- ダミー個人情報を含むものと含まないものを半々にする。**実在の個人情報は使わない**
- 種別ごとに見逃し率・誤検知率を集計し、`src/detector.js` の `SCORE` / `DEFAULT_THRESHOLDS` と `src/rules.js` のキーワード辞書を調整する
- 調整後の値と評価結果を記録し、回帰テストに組み込む

組織で運用する場合は200件以上・誤検知率5%以下を目標値としている（開発ドキュメント 7.4）。個人利用なら30件程度で、明らかな誤検知がないかを見る程度で足りる。

### 3. 対象サイトを広げる

`src/sites.js` にホスト名をキーとしてセレクタを追加し、`manifest.json` の `matches` にドメインを足す。

対象候補: Claude（`claude.ai`）、Gemini（`gemini.google.com`）、Microsoft Copilot（`copilot.microsoft.com`）、Perplexity（`www.perplexity.ai`）。

**過去メッセージの編集欄**や音声入力・キャンバス等の別UIはセレクタが異なることが多く、見逃しの主な原因になる。汎用セレクタ（`PII_GENERIC`）で捕捉できるかを必ず確認すること。

サイトごとに開発ドキュメント 7.3 のチェックリストを実施する。

### 4. 設定画面と件数ログ

- `src/background.js` — 日付×サイト×種別×レベルの**件数のみ**を `chrome.storage.local` に記録。90日で古いキーを削除（Service Worker は常駐しないため、書き込みのたびに削除する）。ツールバーバッジへの件数表示
- `options/` — ルールのON/OFF、カスタムルール、閾値の調整、件数の表示

`src/content.js` には件数を送る `report()` が実装済みで、受け側がいないため現在は握り潰されている。

守ること（[ADR-0008](adr/0008-storage-local-managed-only.md)）:

- `chrome.storage.sync` を使わない（書くだけで Google アカウント経由でクラウド同期される）
- 入力テキスト・検出値を保存しない。`console` へも出力しない
- 保存されるのが「件数」と「設定」だけであることを DevTools で確認する

## 組織で運用する場合に必要になるもの

個人利用では不要。組織配布に進める判断をしたときに着手する。

### 管理者ポリシー

[ADR-0008](adr/0008-storage-local-managed-only.md) で、管理者ポリシー（`chrome.storage.managed`）を**通信しない唯一の設定配信路**と決めている。[ADR-0013](adr/0013-warn-only-with-confirm-popup.md) の `blockRules`（警告からブロックへ引き上げる種別）もここから配る。

- `schema.json` — `lockSettings` / `disabledRules` / `customRules` / `thresholds` / `blockRules` / `blockFileUpload` / `enableNetGuard`
- `manifest.json` への `storage.managed_schema` の登録
- 設定のマージ（`lockSettings: true` のときは managed のみ採用）
- ブロック指定された種別では、確認ポップアップに「このまま送信する」を表示しない

`src/content.js` の `mergeSettings` に `blockRules` による `action` 上書きの経路は実装済みなので、`schema.json` と managed の読み込みを足すことになる。

### 通信ラッパ（最終防御層）

[ADR-0004](adr/0004-network-wrapper-optional.md)。MAIN world に注入して `fetch` / `XMLHttpRequest.send` / `WebSocket.send` をラップし、UIイベントの捕捉が漏れた場合でも送信本文を検査する。

**既定OFF**。ページ側から上書き可能なため主防御にはならず、UIの捕捉漏れに気づくための保険という位置づけ。有効化するとサイトの通常動作を壊すリスクがあるため、初期値で負うべきではない。

`scripts/check-no-network.mjs` の許可リストに `src/net-guard.js` を入れてある（通信APIをラップするため参照が必要）。このファイルは個別レビュー必須。

### 配布基盤

[ADR-0012](adr/0012-forced-install-policy-distribution.md)。社内Webサーバーに CRX と更新マニフェストを置き、`ExtensionInstallForcelist` で強制インストールする。

迂回路を塞ぐポリシーもセットで必要（`DeveloperToolsAvailability`、`IncognitoModeAvailability`、`URLBlocklist` / `URLAllowlist`、他ブラウザの実行制限）。ポリシー名と値はブラウザのバージョンで変わるため、導入時に公式のポリシー一覧で確認すること。

CRX署名鍵の管理方法を決める必要がある（紛失すると更新できなくなる。`.gitignore` で `*.pem` を除外済み）。

### 運用

**AIサービスの画面改修が最大の運用リスク**（[ADR-0011](adr/0011-site-adapter-separation.md)）。セレクタが外れると検査は静かに素通りし、利用者は守られているつもりのまま個人情報を送信する。通信ラッパが既定OFFのため、**壊れたことを自動検知する手段はない**。

- 月1回と、各サービスの大型アップデート告知時に 7.3 のチェックリストを実施する
- セレクタが外れていた場合の修正フロー（`src/sites.js` の更新 → テスト → 再配布）
- 誤検知報告は、**検出値を含めず**「サイト・種別・日時」で受ける

この運用を止めた時点で、防御は静かに劣化する。

## 継続的に見るもの

### `document.execCommand` の代替手段

[ADR-0010](adr/0010-exec-command-for-masking.md) は、入力欄の書き換えに非推奨APIである `document.execCommand('insertText')` を採用している。ProseMirror 等のリッチエディタの内部状態と整合した書き換えを行う、現時点で唯一の現実的な手段のため。

これが動かなくなると、**表示だけマスクされて送信内容は元のまま**という最も危険な失敗が起きる。

再評価のトリガー:

- Chromium が `document.execCommand` を削除、または挙動を変更したとき
- 対象サイトのいずれかで、マスク後の送信内容が一致しない事象が確認されたとき
- 標準化された編集API（`EditContext` 等）が主要サイトのエディタで利用可能になったとき

該当したら新しい ADR を起こして ADR-0010 を置換する。当面は代替フロー（マスク済みテキストをクリップボードにコピーして手動で貼り直す）で機能を維持する。

### ブロックへの引き上げ

[ADR-0013](adr/0013-warn-only-with-confirm-popup.md) で、誤検知の代償が業務停止にならないよう既定の判定を警告のみとした。ブロックは管理者ポリシーの `blockRules` からの有効化経路だけを残してある。

評価コーパスで誤検知率が十分低いと確認できた種別は、後からブロックへ引き上げられる。候補はチェックディジットで自己検証できる保険者番号・マイナンバー・クレジットカード番号。

ただし [ADR-0008](adr/0008-storage-local-managed-only.md) により検出値を保存しないため、件数ログからは「承認された警告が誤検知だったのか本物だったのか」を判別できない。誤検知率の測定は評価コーパスに依存する。

- Enter送信の捕捉 — OK

- 検出なしの通常利用が妨げられない — OK

マスク後の送信内容の一致は、ADR-0010 が非推奨APIに依存して引き受けたリスクそのものなので、**この日付は「いつまでは動いていたか」の基準点**になる。
