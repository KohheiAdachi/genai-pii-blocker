# 調査：後期高齢者医療・公費負担者番号の桁構成と検証方式

- 調査日：2026-09-21
- 対象 issue：#4
- 対象：開発ドキュメント 3.1 で「要確認」としていた3種別
- 結論の要約：**3種別のうち2種別は一次資料で確定できた。1種別（後期高齢者医療 被保険者番号）は全国共通の検証方式を確認できなかった。**

## 0. 結論サマリ

| 種別 | 桁構成 | 検証方式 | 一次資料 | 実装方針 |
| --- | --- | --- | --- | --- |
| 公費負担者番号 | 法別番号2＋都道府県番号2＋実施機関番号3＋**検証番号1**＝8桁 | **あり**（保険者番号と同一のモジュラス10ウェイト2-1） | 設定要領 第２ | `validator: 'luhn'` を適用、キーワード併用 |
| 公費負担医療の受給者番号 | 受給者区分6＋**検証番号1**＝7桁 | **あり**（同上） | 設定要領 第３ | `validator: 'luhn'` を適用、キーワード必須 |
| 後期高齢者医療 被保険者番号 | 数字8桁（全国共通） | **確認できず**（全国共通仕様は見当たらない） | ― | **チェックディジット検証は行わない**。キーワード必須（`requireKeyword: true`） |

開発ドキュメント 3.1 の「要確認」表記は、上2種別について解消できる。3種別目は「確認したが全国共通仕様は存在しないと考えられる」という結論に置き換わる。

## 1. 調査で最も注意すべき点：保険者番号と被保険者番号の混同

**Web上の解説記事の多くが、この2つを混同している。** 調査中に参照した一般向け記事の大半は、「後期高齢者医療の番号は8桁で、法別番号39から始まり、末尾1桁が検証番号」と説明していたが、これは**保険者番号**（後期高齢者医療広域連合を識別する番号）の話であり、被保険者証に記載される**被保険者番号**（個人を識別する番号）の話ではない。

| | 保険者番号 | 被保険者番号 |
| --- | --- | --- |
| 識別する対象 | 後期高齢者医療広域連合（都道府県単位） | 被保険者本人 |
| 桁数 | 8桁 | 8桁 |
| 先頭2桁 | 法別番号 `39` で固定 | 規定なし |
| 検証番号 | **あり**（設定要領 第１の５） | 確認できず |
| 設定者 | 後期高齢者医療広域連合 | 後期高齢者医療広域連合 |

どちらも「8桁の数字」「広域連合が設定」という点が共通しているため、資料を読むときは**どちらの番号の話か**を必ず確認すること。検出ルールとしても別物であり、`insurer_number`（保険者番号）ルールとは別に扱う必要がある。

なお、保険者番号側は既存の `insurer_number` ルール（8桁＋Luhn）でそのまま捕捉できる。法別番号39で始まる8桁は後期高齢者医療の保険者番号である。

## 2. 公費負担者番号（確定）

### 桁構成

設定要領 第２の１より、**法別番号2桁＋都道府県番号2桁＋実施機関番号3桁＋検証番号1桁＝計8桁**の算用数字。

- 法別番号：公費負担医療制度の種類ごとに別表１の(３)で定める（下表）
- 都道府県番号：実施機関の所在地の都道府県ごとに別表２で定める（**01〜47**）
- 実施機関番号：制度の種類ごとに主管行政庁または実施機関が定める
- 検証番号：**第１の５の例により定める**（＝保険者番号と同一のアルゴリズム）

### 検出への反映

- `validator: 'luhn'` をそのまま使える（4節参照）
- 3〜4桁目が `01`〜`47` の範囲にあることを**加点要素**として使える
- 1〜2桁目が既知の法別番号であることも加点要素になるが、法別番号は追加・改正されるため**フィルタ（不一致なら除外）としては使わない**。古いリストによる見逃しを生む

## 3. 公費負担医療の受給者番号（確定・当初の想定と異なる）

設定要領 第３の１より、**受給者区分6桁＋検証番号1桁＝計7桁**の算用数字。第３の３に「検証番号は、第１の５の例により定める」とある。

開発ドキュメント 3.1 では「7桁」「検証番号（要確認）」としていたが、**検証番号は存在し、計算方法も保険者番号と同一**であることが確定した。7桁のうち末尾1桁が検証番号である。

ただし、**7桁の数字がこの検証を偶然通る確率は約10%**（保険者番号と同じ）であり、検証番号の一致だけでは判定できない。受給者区分6桁には構造上の制約がないため、保険者番号のような「都道府県番号が01〜47」といった追加の絞り込みも効かない。**キーワード必須（`requireKeyword: true`）とする**。

## 4. 検証番号のアルゴリズム（設定要領 第１の５）

保険者番号・公費負担者番号・受給者番号・医療機関等コードで**共通**。

1. 検証番号を除く各桁に、末尾の桁を起点として順次 2, 1, 2, 1 … を乗じる
2. 積の和を求める。ただし積が2桁になる場合は、1桁目と2桁目の数字の和とする
3. 10と、2で算出した数字の下1桁との差を求める。これを検証番号とする。ただし1の位が0のときは検証番号を0とする

### Luhn アルゴリズムとの同一性

この手順は Luhn アルゴリズムと**完全に一致する**（末尾から偶数位置を2倍、積が2桁なら桁和＝9を引く操作と等価、チェック digit は `(10 - sum % 10) % 10`）。

したがって `detector.js` に**新しいバリデータを追加する必要はない**。既存の `luhn` を、桁数の異なるルールから参照すればよい。

```js
// 既存の luhn バリデータがそのまま使える
// 保険者番号（8桁/6桁）、公費負担者番号（8桁）、受給者番号（7桁）で共通
const digitSum = (n) => (n < 10 ? n : Math.floor(n / 10) + (n % 10));
const checkDigit = (payload) => {
  let s = 0;
  [...payload].reverse().forEach((c, i) => { s += digitSum(Number(c) * (i % 2 === 0 ? 2 : 1)); });
  return (10 - (s % 10)) % 10;
};
```

### 通知の計算例（原文）

設定要領 第１の５の例は、PDFのレイアウト上で桁がずれて読み取りにくいが、印刷されている積の和「22」と検証番号「8」から復元すると **`06130488`**（法別06・都道府県13・保険者別048・検証8）となる。

```
   0   6   1   3   0   4   8   ⑧ ← 検証番号
   ×   ×   ×   ×   ×   ×   ×
   2   1   2   1   2   1   2
   0 + 6 + 2 + 3 + 0 + 4 + (1+6) = 22
   10 - 2 = 8
```

復元値で再計算すると検証番号は8となり、通知の記載と一致する。

## 5. 後期高齢者医療 被保険者番号（全国共通の検証方式は確認できず）

### 確認できたこと

- **数字8桁**であることは全国共通。国保連合会のレセプト返戻事例に「後期高齢者の被保険者番号は数字8桁に設定されています。数字8桁以外での記載の場合は返戻扱いになります」と明記されている
- 後期高齢者医療の被保険者番号は、健保等に先行して**個人単位で付番**されている（オンライン資格確認の個人単位化にあたり、後期高齢者医療は既に個人単位のためそのまま用いる、と整理されている）
- 健康保険等では2桁の**枝番**が2021年から追加されたが、後期高齢者医療の被保険者番号にはこの枝番の概念がない

### 確認できなかったこと

- **検証番号（チェックディジット）の全国共通の計算方法**
- 8桁の内部構造（先頭に広域連合を示す固定値があるか等）

「保険者番号、公費負担者番号、公費負担医療の受給者番号並びに医療機関コード及び薬局コード設定要領」は**被保険者番号を対象としていない**（文書中に「被保険者番号」の語が1度も現れない）。付番は各広域連合が行うと整理されており、全国共通の付番規則を定めた公開資料は見つけられなかった。

### 実装方針（ADR-0005 の暫定方針を確定方針とする）

**チェックディジットでの絞り込みは行わない。キーワード必須の判定に留める。**

```js
{
  id: 'koukikoureisha_insured_number', label: '後期高齢者医療 被保険者番号', kind: 'numeric',
  lengths: [8], validator: null, action: 'warn', requireKeyword: true,
  keywords: {
    strong: ['後期高齢', '被保険者番号', '高齢受給者', '資格確認書'],
    weak: ['番号', '保険証'],
    negative: ['保険者番号', '注文番号', '郵便番号', '型番']
  }
}
```

`negative` に `保険者番号` を入れているのは、1節で述べた混同を検出側でも避けるため（保険者番号は `insurer_number` ルールが担当する）。

### 追加調査の選択肢（必要になったら）

1. 自組織が所在する都道府県の後期高齢者医療広域連合に、被保険者番号の付番規則を直接照会する
2. 国保中央会「後期高齢者医療広域連合電算処理システム」の標準仕様書（一般公開されていない可能性が高い）
3. 各広域連合の例規集で「被保険者証等の交付に関する要綱」等を確認する

ただし、**仮に特定の広域連合の付番規則が判明しても、全国の広域連合で共通とは限らない**。全国共通でない検証方式を実装すると、他県の番号を見逃す。キーワード必須の方針は、この点でも妥当と考える。

## 6. 付随して判明したこと：告知要求制限（開発ドキュメント 6.5 の裏付け）

開発ドキュメント 6.5 で「健康保険法等で告知の求めが制限されている情報」と書いていた点について、根拠条文が確認できた。

- **令和2年10月1日施行**
- 健康保険法 第194条の2 第1項、船員保険法 第143条の2 第1項、国民健康保険法 第111条の2 第1項、**高齢者の医療の確保に関する法律 第161条の2 第1項**、私立学校教職員共済法 第45条 第1項、国家公務員共済組合法 第112条の2 第1項、地方公務員等共済組合法 第144条の24の2 第1項
- 内容：プライバシー保護の観点から、**健康保険事業またはこれに関連する事務の遂行等の目的以外で**、被保険者等記号・番号等の告知を求めることを禁止する
- 対象には**後期高齢者医療の被保険者番号も含まれる**（高齢者医療確保法が対象法律に含まれるため）

本拡張の直接の根拠規定ではないが、「これらの番号は目的外の告知を求めること自体が制限されている」という位置づけは、社内規程や利用者への説明の材料になる。条文の当てはめは法務・情報セキュリティ部門に確認すること（開発ドキュメント 6.5）。
