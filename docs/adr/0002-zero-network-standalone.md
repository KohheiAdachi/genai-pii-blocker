# ADR-0002: 拡張機能を完全スタンドアロン（外部通信ゼロ）とし、4層で担保する

- ステータス：採用
- 日付：2026-09-20
- 関連：開発ドキュメント 1.3, 6.1, 6.2

## コンテキスト

本拡張は、利用者が入力した**個人情報そのもの**を常時読み取る。もしこの拡張が外部と通信できるなら、拡張機能自体が情報漏えい経路になりうる。個人情報保護の仕組みが新たな委託先・越境移転の論点を生むのでは本末転倒であり、情報セキュリティ部門の審査も通らない。

一方で、検出ルールをサーバー配信にしたい、検出ログを中央集約したい、判定をLLMに任せたいといった要求は自然に発生する。ここで境界を引いておかないと、後から通信が少しずつ混入する。

## 決定

拡張機能のコードは外部通信APIを一切使用しない。これを規約だけに頼らず、次の4層で機械的に担保する。

| 層 | 対策 |
| --- | --- |
| コード | `fetch`・`XMLHttpRequest`・`WebSocket`・`EventSource`・`navigator.sendBeacon`・`import()` を使わない。依存ライブラリはゼロを原則とする |
| ビルド | `scripts/check-no-network.mjs` が上記API名と `http://` / `https://` 文字列の混入を検出し、見つかればビルドを失敗させる。例外は `src/net-guard.js` のみ（許可リスト・個別レビュー） |
| CSP | `extension_pages` に `connect-src 'none'` を指定し、設定画面とService Workerからの通信をブラウザに拒否させる |
| 権限 | `webRequest`・`<all_urls>`・`identity`・`tabs` を要求しない。`host_permissions` は対象AIドメインのみ |

加えてリリース前に DevTools Network パネルと `chrome://net-export` で拡張機能起点の通信が0件であることを確認する。

## 理由

- 「通信しない」は**宣言では証明できない**。ビルドで落ちる仕組みとCSPによるブラウザ側の拒否があって初めて、レビューと監査に耐える主張になる
- ルール配信やログ集約は、通信ではなく**managed storage（ブラウザポリシー）**という既存経路で代替できる（ADR-0008）。ポリシー配布はブラウザ本体が行うため、拡張機能自身は通信しない
- 依存ライブラリをゼロにすることで、サプライチェーン経由で通信コードが混入する余地も同時に消える

## 代替案

| 案 | 却下理由 |
| --- | --- |
| 社内サーバーでの検出API / LLM判定 | 入力テキスト全文をネットワークに出すことになり、防ごうとしている行為を拡張機能自身が行う |
| 検出ルールのサーバー配信（fetch） | 通信ゼロの主張が崩れ、4層の担保が成立しなくなる。ポリシーと同梱ルールの更新で代替できる |
| ログの中央集約（SIEM送信） | 検出値を送らなくても通信経路が必要になる。件数の把握は設定画面での参照と、必要なら端末管理ツール側の収集で足りる |
| コード規約とレビューのみで担保 | 人手のレビューは漏れる。後からの改修で静かに壊れる |

## 結果

**得られるもの**

- 「この拡張機能は通信しない」を、コード・ビルド・ブラウザ設定・権限の4点で示せる
- 審査・導入判断の説明コストが下がる

**引き受けるもの**

- 検出ルールの緊急更新は、拡張機能の再配布か管理者ポリシーの変更でしか行えない（8.3）
- 組織横断での検出傾向の可視化は、この拡張単体ではできない
- ビルドチェックの正規表現は文字列 `fetch(` 等を機械的に見るため、コメントや無関係な変数名にも反応する。許可リストの運用が必要になる
- コンテンツスクリプトは**ページのCSP**の下で動くため拡張機能のCSPでは縛れない。この範囲はコード規約とビルドチェックのみで守る（層が1つ減る）
