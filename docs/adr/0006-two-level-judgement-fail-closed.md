# ADR-0006: 判定をブロック／警告の2段階とし、例外時はfail-closedとする

- ステータス：採用
- 日付：2026-09-20
- 関連：開発ドキュメント 1.3, 2.2, 5.6, 5.7、ADR-0005

## コンテキスト

すべての検出を一律ブロックにすると、電話番号やメールアドレスを含む正当な業務利用（社外向け文面の推敲など）まで止まり、利用者は拡張機能そのものを回避する動機を持つ。一方、すべてを警告にすると、健康保険の被保険者番号のように**絶対に出してはならない情報**が利用者の判断で送信されてしまう。

また、検出エンジンが例外を投げた場合に「通す」のか「止める」のかを決めておく必要がある。

## 決定

**判定を2段階とする。**

| レベル | 対象 | 挙動 |
| --- | --- | --- |
| ブロック | 保険者番号、被保険者記号・番号、マイナンバー、基礎年金番号、クレジットカード番号 | 送信不可。「マスクする」「編集に戻る」の2択 |
| 警告 | 電話番号、メールアドレス、免許証番号、パスポート番号、生年月日＋氏名、病名・診療情報 | 確認のうえ送信可。「このまま送信する」を追加 |

**警告の承認は、同一テキストかつ10秒以内の再送信のみ有効**とする（`approved = { text, until }`、消費したら破棄）。

**例外時はfail-closed**：`Detector.detect()` が例外を投げた場合は送信を中止し、エラーモーダルを表示する。

## 理由

- 「誤検知より見逃しを重く見る」（1.3）という原則を、**対象ごとに**適用する。要配慮情報に直結する番号は利用者の裁量から外し、それ以外は業務を止めない
- 承認を**テキスト一致＋10秒**に限定するのは、一度の「このまま送信」が以降の入力にまで効いてしまうと、警告が実質的に無効化されるため。テキストを編集すれば再検査される
- **fail-closed**：検査できなかった状態は「安全が確認できていない」状態である。バグや想定外の入力で防御が静かに外れるより、送信を止めて気づかせる方が被害が小さい
- ブロック時に「マスクする」を必ず提示することで、利用者に**代替手段**を与える。止めるだけでは回避行動（別ブラウザ、スマホ）を誘発する

## 代替案

| 案 | 却下理由 |
| --- | --- |
| すべてブロック | 電話番号・メールアドレスを含む正当な業務利用を阻害し、拡張機能の回避を促す |
| すべて警告（確認ダイアログのみ） | 慣れによる反射的な承認で、最も守りたい番号が送信される。F-06の要件に反する |
| 承認を「このセッション中」有効にする | 一度承認すると以降の入力が無検査になる。警告が形骸化する |
| 例外時は通す（fail-open） | 検出エンジンのバグや未知の入力で防御が無言で外れる。利用者も管理者も気づけない |
| 管理者承認フロー（申請して解除） | 承認の待ち時間が業務を止める。通信ゼロ（ADR-0002）のため申請経路も拡張機能内には作れない |

## 結果

**得られるもの**

- 守るべき情報を利用者の裁量から外しつつ、日常業務の妨げを最小化できる
- 防御が外れる方向の失敗をしない

**引き受けるもの**

- 警告を承認して送信された分は防げない。件数ログ（ADR-0008）で傾向を把握し、警告対象を必要最小限に保つ運用が必要になる（8.4）
- fail-closedのため、検出エンジンの不具合がそのまま**業務停止**につながる。単体テストの網羅（7.2）と、エラーモーダルから管理者へ連絡する導線が前提となる
- 10秒という値は体感に基づく暫定値であり、実機テストで調整しうる
