# ADR-0003: 主防御をISOLATED worldでのUIイベントcapture捕捉に置く

- ステータス：採用
- 日付：2026-09-20
- 関連：開発ドキュメント 4.3, 4.4, 6.4

## コンテキスト

送信を止められる地点は複数ある。

1. 利用者の送信操作（Enter、送信ボタン、フォーム送信）を横取りする
2. ページが組み立てたリクエスト（`fetch` 等）の本文を検査する
3. ブラウザの `webRequest` でリクエストを遮断する

どこを主防御に置くかで、検出漏れの起き方も、ページ側から回避される余地も変わる。特に「ページのスクリプトが検査ロジックを書き換えられるか」は、防御の前提そのものを左右する。

## 決定

主防御は、コンテンツスクリプト（**ISOLATED world**、`run_at: document_start`）が `window` に `capture: true` で登録したリスナーによるUIイベント捕捉とする。

- 捕捉対象：`keydown`（Enter。`isComposing` / `keyCode === 229` / Shift+Enter は除外）、`pointerdown` / `click`（送信ボタン）、`submit`、`paste`、`drop`、`beforeinput`
- 検出時は `preventDefault()` と `stopImmediatePropagation()` でサイト側ハンドラに到達させない
- 入力欄はSPA遷移で作り直されるため `MutationObserver` で出現を監視する

## 理由

- **capture フェーズ＋`document_start`**により、サイト自身のハンドラより先に実行される。サイトのバンドルが読み込まれる前にリスナーが載るため、登録順の競争に勝てる
- **ISOLATED world**ではページのスクリプトから検出ロジックも設定も参照・書き換えができない。MAIN worldに置いた場合、ページ側（あるいはページに注入された任意のスクリプト）から無効化されうる
- 送信前の**平文**をDOMから直接読めるため、サービスごとに異なるリクエスト形式（JSON、ストリーム、multipart）を解釈しなくて済む
- 貼り付け・ドロップを `paste` / `drop` の段階で止められるので、個人情報が入力欄に入る前に遮断できる

## 代替案

| 案 | 却下理由 |
| --- | --- |
| MAIN worldの通信ラッパを主防御にする | ページ側から `window.fetch` を復元・上書きされうるため、防御として信頼できない。ただし捕捉漏れの補完には有用なので補助層として採用する（ADR-0004） |
| `chrome.webRequest` のblockingで遮断 | MV3ではポリシー強制インストール時に限り利用できるが、リクエスト本文の扱いに制約が大きい。加えてブロック理由を入力画面に返せず、利用者がマスクして送り直す導線を作れない |
| bubbleフェーズで捕捉 | サイト側が `stopPropagation()` を呼ぶと到達しない。送信が先に実行される |
| 入力欄の `input` イベントのみを監視し、検出したら入力欄を書き換える | 入力中の割り込みは操作性を大きく損ねる。リアルタイム検出はバッジ表示（F-07）に留め、遮断は送信操作の時点で行う |

## 結果

**得られるもの**

- ページのスクリプトから無効化されない防御位置を確保できる
- 送信経路がEnterでもボタンでも貼り付けでも、同じ検査ロジックを通せる

**引き受けるもの**

- **UIの構造に依存する**。送信ボタンのDOMが変わる、新しい送信ショートカットが増える、過去メッセージの編集欄など別UIが追加される、といった改修で捕捉漏れが起きる。これを前提に、サイトアダプタの分離（ADR-0011）、汎用セレクタでのフォールバック、通信ラッパ（ADR-0004）、月次の実機チェック（7.3）で補う
- `all_frames: true` での注入となるため、iframe内での多重実行を考慮した実装が必要になる
- IME変換確定のEnterを送信と誤認すると日本語入力が壊れる。`isComposing` の扱いはサイト別チェックリストの必須項目とする
