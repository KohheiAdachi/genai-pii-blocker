# ADR-0010: 入力欄の書き換えに `document.execCommand('insertText')` を用いる

- ステータス：採用（要再評価）
- 日付：2026-09-20
- 関連：開発ドキュメント 5.6、ADR-0006

## コンテキスト

F-05「該当箇所をマスクして入力欄に戻す」を実現するには、AIサイトの入力欄のテキストを書き換える必要がある。ところが対象サイトの入力欄は ChatGPT・Claude を含めて ProseMirror 系の `contenteditable` が主流で、React などのフレームワークが内部状態を別に保持している。

`element.innerText = '...'` や `textarea.value = '...'` で直接書き換えると、**DOMだけが変わり内部状態が古いまま**になる。結果として、利用者にはマスクされて見えるのに、送信されるのはマスク前のテキストという最悪の失敗が起きうる。マスク機能が信頼できないなら、ブロック時に代替手段を提示できず、利用者は拡張機能を回避しようとする（ADR-0006）。

## 決定

入力欄の種類に応じて、フレームワークの内部状態が追従する方法で書き換える。

- **`textarea`**：`HTMLTextAreaElement.prototype` の `value` セッターを `Object.getOwnPropertyDescriptor` で取り出して呼び、`new Event('input', { bubbles: true })` を発火する（Reactの合成イベントに拾わせる）
- **`contenteditable`**：`Range` で全選択したうえで `document.execCommand('insertText', false, newText)` を実行する

`document.execCommand` が非推奨APIであることを承知のうえで採用する。**マスクに失敗した場合の代替フロー**として、「マスク済みテキストをクリップボードにコピーし、利用者に手動で貼り直してもらう」導線を用意する。

## 理由

- `execCommand('insertText')` はブラウザのネイティブな編集操作として扱われ、`beforeinput` / `input` イベントが正規の経路で発火する。ProseMirror や Lexical はこれを購読しているため、**内部状態が整合したまま**更新される
- Reactの `textarea` は `value` プロパティを自前で追跡するため、prototypeのセッターを経由して書き込まないと変更が検知されない。これはReact環境で広く使われている既知の手法である
- 非推奨ではあるが、`execCommand('insertText')` は**すべての主要ブラウザで現に動作**しており、Chromiumに代替APIが実装されるまでは実用上の唯一の選択肢である
- 失敗時の代替フローを用意することで、この決定が将来崩れても**機能の完全な喪失にはならない**

## 代替案

| 案 | 却下理由 |
| --- | --- |
| `innerText` / `value` への直接代入 | フレームワークの内部状態が追従せず、表示と送信内容が食い違う。**マスクしたつもりで送信される**という最悪の失敗を生む |
| `InputEvent` を手動で合成して `dispatchEvent` | 合成イベントは `isTrusted === false` であり、エディタ実装によっては無視される。挙動がサイトごとにばらつく |
| クリップボード経由のみ（手動で貼り直し） | 確実だが操作が増え、利用者の負担が大きい。既定の導線には向かない。**代替フローとしては採用**する |
| マスク機能を提供せず「編集に戻る」だけにする | 利用者が自分で該当箇所を探して消すことになる。回避行動を誘発する（ADR-0006） |
| サイトごとにエディタAPI（ProseMirror等）を直接叩く | サイトの内部実装に依存し、保守不能になる。MAIN worldでの実行も必要になる |

## 結果

**得られるもの**

- 主要サイトで、表示と送信内容が一致したマスクが行える
- サイト固有のエディタ実装に踏み込まずに済む

**引き受けるもの**

- **非推奨APIへの依存**を抱える。Chromiumが削除した時点で代替フローへの切り替えが必要になる
- サイト別チェックリストに「マスクで入力欄が書き換わり、サイト側の送信内容にも反映される」項目を必須で含める（7.3）。この検証は自動化しにくく、実機での確認が要る
- 全選択してから挿入するため、利用者の未確定のIME入力やカーソル位置は失われる

## 再評価のトリガー

- Chromiumが `document.execCommand` を削除、または挙動を変更したとき
- 対象サイトのいずれかで、マスク後の送信内容が一致しない事象が確認されたとき
- 標準化された編集API（`EditContext` 等）が主要サイトのエディタで利用可能になったとき
