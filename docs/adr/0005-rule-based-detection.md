# ADR-0005: 検出方式をルールベース（正規化→正規表現→検証桁→文脈スコア）とする

- ステータス：採用
- 日付：2026-09-20
- 関連：開発ドキュメント 3, 5.3, 5.4, 7.4

## コンテキスト

検出したい情報の中心は健康保険関連の番号である。ここには性質の異なる2種類が混ざっている。

- **自己検証できるもの**：保険者番号（検証番号）、マイナンバー（検査用数字）、クレジットカード番号（Luhn）
- **自己検証できないもの**：被保険者記号・番号（保険者ごとに可変長の英数字）、基礎年金番号、運転免許証番号

後者は「数字列」としては注文番号や型番と区別がつかない。桁数だけで判定すれば誤検知が業務を止め、キーワードを必須にすれば見逃す。さらにADR-0002により、判定を外部のモデルに投げることはできない。

## 決定

端末内で完結するルールベースの多段判定とする。

1. **正規化**：`NFKC` で全角を半角化、ハイフン類を `-` に統一、数字間の区切りを除いた「数字列ビュー」を作る。元テキストとの**位置対応表**を保持する（マスク時に元の位置を置換するため）
2. **パターン照合**：正規表現または桁数指定で候補を抽出する
3. **チェックディジット検証**：保険者番号（Luhn相当）、マイナンバー（mod 11）、カード番号（Luhn）
4. **文脈スコアリング**：候補の前後40文字をキーワード辞書と照合し加点・減点する

| 要素 | 加点 |
| --- | --- |
| 形式一致 | +30 |
| チェックディジット一致 | +40 |
| 強キーワード（被保険者、保険者番号、マイナンバー 等） | +40 |
| 弱キーワード（番号、患者、カルテ、生年月日 等） | +15 |
| 否定キーワード（注文番号、型番、郵便番号、ISBN 等） | −40 |

5. **判定**：70点以上で当該ルールの既定判定、40〜69点は警告、39点以下は通過（ADR-0006）

閾値とキーワードは設定ファイルで調整可能とし、**200件以上の評価コーパス**で決定する（7.4）。漢数字の数字化は誤検知が多いため初期版では行わない。

## 理由

- **チェックディジットだけでは足りない**。8桁の数字がLuhnを通る確率は約10%あり、業務文書中の任意の数字列が偶然一致する。そのため `requireKeywordForBlock` により、キーワードのない自己検証番号はブロックではなく警告に留める
- **キーワードだけでも足りない**。「番号」は日常語であり、否定キーワードによる減点と組み合わせて初めて実用になる
- **スコアの合算**にすることで、単一条件のしきい値調整ではなく、評価コーパスに対する総合的なチューニングが可能になる
- **正規化と位置対応表**は、全角入力（`０６１３００１７`）や区切り付き（`0613-0017`）を検出しつつ、マスク時に元テキストを正しく置換するために必須である
- ルールとスコアは**説明可能**であり、モーダルで「なぜ止めたか」（検証番号一致、キーワード一致）を提示できる。これはF-04の要件そのものである

## 代替案

| 案 | 却下理由 |
| --- | --- |
| LLM / クラウドAPIでの判定 | ADR-0002の通信ゼロに反する。入力全文を外部に出すことになる |
| 端末内の機械学習モデル（NER等） | 拡張機能に同梱できるサイズと推論時間の制約が厳しい（1万文字を50ms以内、2.2）。判定根拠を利用者に示せず、誤検知時の調整手段が「再学習」になり運用に乗らない。依存ゼロ方針（ADR-0002）とも衝突する |
| 正規表現のみ（スコアなし） | 誤検知が多すぎて業務を止めるか、緩めて見逃すかの二択になる |
| チェックディジット必須 | 被保険者記号・番号や基礎年金番号など、検証方式を持たない主要対象が検出できない |
| 漢数字の数字化を初期版から入れる | 「一つの番号」のような通常文への誤検知が多く、費用対効果が低い。将来オプションとする |

## 結果

**得られるもの**

- 判定根拠が説明可能で、誤検知報告に対してルール単位で対処できる
- 端末内・50ms以内という性能要件を満たせる

**引き受けるもの**

- キーワード辞書と閾値の**継続的なチューニング**が必要になる。評価結果はリリースノートに残し、回帰テストに使う（7.4）
- 文脈を持たない裸の番号、分割入力、読み上げ表記は検出できない。残存リスクとして運用で補う（8.4）
- 保険者番号以外の公的番号（後期高齢者医療、公費負担者番号）の**検証方式は未確認**であり、確認できるまではキーワード必須の判定に留め、チェックディジットでの絞り込みは行わない（3.1の「要確認」）
  - **2026-09-21 追記：調査により解決した。8節を参照。**

## 再評価のトリガー

- 評価コーパスで誤検知率が目標（5%以下）に収束しないとき
- 端末内で動作する軽量なNERモデルが、サイズ・速度・説明性の制約を満たせるようになったとき

## 追記（2026-09-21）：未確認だった検証方式の調査結果

「引き受けるもの」に未確認として残していた3種別を調査した（issue #4）。**この決定自体は変わらない**（ルールベースの多段判定を続ける）。確定した事実と、それに伴う運用方針だけを記録する。

調査記録：`docs/research/2026-09-21-kouhi-koukikoureisha-number-format.md`

| 種別 | 結果 | このADRでの扱い |
| --- | --- | --- |
| 公費負担者番号（8桁） | 検証番号**あり**。保険者番号と同一のアルゴリズム | 「チェックディジット検証」の対象に加える |
| 公費負担医療の受給者番号（7桁） | 受給者区分6桁＋検証番号1桁。検証番号**あり** | 同上。ただし7桁に構造上の制約がないため**キーワード必須**とする |
| 後期高齢者医療 被保険者番号（8桁） | 全国共通の検証方式を**確認できなかった**（設定要領の対象外で、付番は各広域連合が行う） | **チェックディジット検証は行わない。キーワード必須を恒久的な方針とする** |

補足：

- 保険者番号・公費負担者番号・受給者番号・医療機関等コードの検証番号は**すべて同一のアルゴリズム**であり、これは Luhn と一致する。`detector.js` に新しいバリデータを追加する必要はなく、既存の `luhn` を桁数違いのルールから参照すればよい
- 後期高齢者医療については、特定の広域連合の付番規則が判明しても全国共通とは限らない。全国共通でない検証方式を実装すると他県の番号を見逃すため、**追加調査を行わない**ことを選択した
- Web上の解説の多くが**保険者番号（広域連合の番号）と被保険者番号（個人の番号）を混同**している。ルール設計では別物として扱い、後期高齢者医療 被保険者番号のルールには否定キーワードとして「保険者番号」を入れる
