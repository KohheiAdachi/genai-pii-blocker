# ADR-0007: 検出ルールをJSONファイルではなくJSモジュールとして同梱する

- ステータス：採用
- 日付：2026-09-20
- 関連：開発ドキュメント 3.6, 5.1, 5.3、ADR-0002

## コンテキスト

検出ルールは「データ」であり、素直に考えれば `rules.json` に置いて読み込む。しかし拡張機能内のJSONを読むには、コンテンツスクリプトから

```js
const rules = await fetch(chrome.runtime.getURL('rules.json')).then(r => r.json());
```

とするのが一般的であり、これは `fetch` の呼び出しになる。ADR-0002のビルドチェックは `fetch(` を機械的に検出してビルドを失敗させるため、ここで例外を作ることになる。

例外を1つ作ると、「拡張機能内のURLなら安全」という判断をレビューのたびに繰り返すことになり、通信ゼロの機械的な担保が緩む。

## 決定

同梱ルールは `src/rules.js` としてJSで定義し、`globalThis.PII_RULES` に置く。`manifest.json` の `content_scripts.js` に他のスクリプトと並べて列挙し、ブラウザに読み込ませる。サイトアダプタ（`sites.js`）も同じ理由でJSとする。

ルール自体は**データ構造のまま**（オブジェクトの配列）記述し、関数やロジックを持ち込まない。バリデータは `validator: 'luhn'` のように**名前で参照**し、実体は `detector.js` に置く。

## 理由

- **`fetch` の使用を例外なくゼロにできる**。ビルドチェックに許可リストの穴を開けずに済み、ADR-0002の担保が単純なまま保たれる
- ルールの内容と管理方法は変わらない。JSONの構造をそのままJSのオブジェクトリテラルで書くだけであり、失うものがない
- ファイルの読み込み順を `manifest.json` で宣言できるため、非同期の初期化待ちが不要になる。`document_start` で即座に検査可能な状態を作れる（ADR-0003）
- ルールに関数を持ち込まない制約により、管理者ポリシー由来のカスタムルール（`customRules`）と**同じ形式**を保てる。ポリシー経由で任意コードが注入される余地も生まれない

## 代替案

| 案 | 却下理由 |
| --- | --- |
| `rules.json` を `fetch(chrome.runtime.getURL(...))` で読む | ビルドチェックに例外が必要になり、通信ゼロの機械的担保が緩む |
| `rules.json` をビルド時にJSへ変換する | 結果は同じだが、ビルド工程とソースの二重管理が増える。依存ゼロ・ビルドレスの方針に反する |
| ルールをService Workerが読んでメッセージで配る | 初期化が非同期になり、`document_start` 直後の入力を取りこぼす。Service Workerの起動待ちも挟まる |
| ルールに関数（カスタムバリデータ）を書けるようにする | 管理者ポリシー経由のカスタムルールと形式が揃わなくなる。ポリシーから任意コードを流し込む経路になりうる |

## 結果

**得られるもの**

- 拡張機能のコードに `fetch` が1箇所も存在しない状態を維持できる
- ルールが同期的に利用可能で、初期化の競合を考えなくてよい

**引き受けるもの**

- ルールがJSファイルであるため、**構文エラーがそのまま検出機能の停止**につながる。ルール変更時は単体テスト（7.2）の実行を必須とする
- JSON Schemaによるルール定義の検証がそのままでは使えない。必要ならテスト側で構造を検査する
- ルールファイルを非エンジニアが直接編集する運用には向かない。運用上の追加・変更は管理者ポリシーの `customRules` を正とする（ADR-0008）
