# ADR-0013: 既定の判定を警告のみとし、送信前の確認ポップアップで止める

- ステータス：採用
- 日付：2026-09-21
- 置換：ADR-0006（2段階判定）を置き換える
- 関連：開発ドキュメント 1.3, 2.1, 3.1, 3.5, 5.6, 5.7、ADR-0003, ADR-0005, ADR-0008, ADR-0009, ADR-0012

## コンテキスト

ADR-0006 は、保険者番号・マイナンバー・クレジットカード番号などを**ブロック（送信不可）**、それ以外を警告とする2段階判定を採用した。運用を具体的に詰めた結果、この割り当てには次の問題があることが分かった。

- **誤検知は原理的に避けられない**。ADR-0005 のとおり、8桁の数字がLuhn相当の検証を偶然通る確率は約10%あり、キーワード辞書も業務ごとの語彙に依存する。閾値は評価コーパス（7.4）で調整するが、**導入前に誤検知率を確定できない**
- **ブロックには逃げ道がない**。誤検知が起きたとき、利用者は送信できない。ADR-0012 の強制インストールと設定固定が組み合わさると、利用者側での回避手段は存在せず、**誤検知がそのまま業務停止になる**（ADR-0012「引き受けるもの」に記載済み）
- **回避行動を誘発する**。止められた利用者は、別ブラウザ・スマートフォン・デスクトップアプリへ移る。そこは拡張機能の対象外であり、完全に無防備になる（8.4）

一方で「送信前に止める」こと自体（ADR-0001の前提）は手放せない。送信後に通知しても、情報はすでに外部へ渡っている。

## 決定

**既定の判定を警告のみとし、警告時は送信をいったん止めて確認ポップアップを表示する。**

1. **同梱ルールの既定 `action` はすべて `warn`**。どの種別にも既定でブロックを割り当てない
2. **検出時は送信操作をいったん止める**。ADR-0003 の捕捉機構（`preventDefault()` ＋ `stopImmediatePropagation()`）はそのまま使い、利用者が承認したときだけ送信する
3. **確認ポップアップのボタンは3つ**：「マスクする」「編集に戻る」「このまま送信する」。承認は**同一テキスト・10秒以内の再送信のみ**有効（ADR-0006 から継承）
4. **貼り付け・ドロップも同様に**いったん止めてポップアップを出し、「このまま貼り付ける」で続行できる
5. **スコアの段階は「重要度」として残す**：70点以上は警告（強調表示）、40〜69点は警告（参考）、39点以下は通過
6. **ブロックは管理者ポリシー（managed storage）から種別ごとに有効化できる経路のみ残す**。既定値は配布時も警告
7. **fail-closed は維持するが、利用者が続行できる形に変える**：検出エンジンが例外を投げた場合も送信を中止してエラーポップアップを表示し、「このまま送信する」で続行できる

## 理由

- **誤検知の代償が1クリックに収まる**。ブロックでは誤検知の代償が業務停止だった。警告なら、拡張機能が間違えたときのコストを利用者が即座に清算できる
- **防止策としての価値は落ちない**。止める地点は送信**前**のままであり、利用者は個人情報が外部へ出る前に気づける。事後通知との決定的な違いはここにある
- **拡張機能が使われ続けることが最大の防御**である。回避行動を誘発しない設計は、ブロックの強制力より実効性が高い
- **段階的に導入できる**。ADR-0008 の件数ログ（日付×サイト×種別×レベル）で「警告後に送信された件数」の傾向を把握し、誤検知率が十分低いと確認できた種別だけを、後からポリシーでブロックへ引き上げられる
- **ポリシー経由のブロックを残す**のは、その引き上げに再設計を必要としないため。判定レベルの概念自体を削除すると、将来の導入が大きな変更になる
- **fail-closed の続行可**：ADR-0006 の fail-closed は、検出エンジンの不具合が業務停止に直結するという副作用を持っていた。止めて気づかせるという目的は確認ポップアップで達成でき、業務停止の副作用だけを外せる

## 代替案

| 案 | 却下理由 |
| --- | --- |
| ADR-0006 のまま（種別ごとのブロック） | 誤検知時に逃げ道がなく、強制インストールと組み合わさると業務停止になる。回避行動を誘発する |
| 送信は止めず、事後にポップアップで通知するだけ | 送信後では手遅れで、防止策として成立しない。ADR-0001 の「送信前に止める」という前提に反する |
| 入力中のバッジ表示のみ（F-07）で送信操作には介入しない | 集中しているときほど見落とす。気づかせる仕組みとしては弱い |
| ブロックという判定レベル自体を削除する | 実装は単純になるが、評価で誤検知率が十分低いと確認できた種別を後から引き上げる際に再設計が必要になる。ポリシー経路を残すコストは小さい |
| マイナンバー・カード番号など自己検証できる種別だけブロックを残す | チェックディジットを通る偶然の一致（約10%）があるため「確実」とは言えない。例外を残すと、誤検知時の業務停止リスクも残る |
| 管理者への申請・承認フローで解除する | ADR-0002 の通信ゼロのため拡張機能内に申請経路を作れない。待ち時間も業務を止める |

## 結果

**得られるもの**

- 誤検知が業務を止めない。拡張機能が回避されにくくなる
- 送信前に気づける点は維持される
- 件数ログを根拠に、種別ごとの段階的な強化が可能になる
- fail-closed でも業務が止まらない

**引き受けるもの**

- **利用者が承認すれば送信される**。慣れによる反射的な承認は防げない。警告の対象を必要最小限に保ち、ポップアップには「なぜ止めたか」（検証番号一致、キーワード一致）を具体的に示して、承認の判断材料を与える
- **「このまま送信する」ボタンが常に存在する**ことになり、これを押させれば全防御が外れる。ADR-0009 の closed Shadow DOM と `event.isTrusted` の検証は、**推奨ではなく必須要件**に格上げする
- ADR-0008 により検出値を保存しないため、件数ログからは「承認された警告が誤検知だったのか、本物だったのか」を判別できない。誤検知率の測定は評価コーパス（7.4）に依存する
- 開発ドキュメントの既定判定（3.1）、機能要件 F-06（2.1）、`rules.js` の `action`（5.3）、モーダル仕様（5.7）、テストベクタ（7.2）を警告基準に揃える必要がある

## 再評価のトリガー

- 評価コーパスで、特定種別の誤検知率が十分低いと確認できたとき（ポリシーによるブロック昇格の検討）
- 件数ログで「警告後に送信された件数」が高止まりし、警告が形骸化していると判断されたとき
